# 文件会话记忆

恋爱助手使用 `FileBasedChatMemory` 保存消息，默认目录为项目运行目录下的 `tmp/chat-memory/`。`ChatMemoryConfig` 创建存储对象，`LoveApp` 通过依赖注入使用它；同步和 SSE 请求使用同一套规则。

## 为什么要限制历史

用户的一句话和 AI 的一条回复各算一条消息。磁盘保存和模型上下文是两个不同的上限：

| 配置 | 默认值 | 含义 |
| --- | --- | --- |
| `app.chat-memory.max-stored-messages` | 200 | 每个会话在磁盘中最多保留的最近消息数 |
| `app.chat-memory.max-context-messages` | 20 | `ChatMemory.get(id)` 交给模型的最近历史消息数 |
| `app.chat-memory.directory` | `tmp/chat-memory/` | 存储目录，可指定绝对路径；相对路径以运行目录为基准 |

例如磁盘已有 200 条消息时再保存一条，最早一条会被移除，保留最近 200 条。模型请求只携带其中最近 20 条历史，另外仍包含当前问题和系统提示词。较早但仍在磁盘保留范围内的内容不会因一次上下文读取而删除。

`get(id, lastN)` 是显式读取已保留历史的扩展方法，最多返回磁盘上限数量；默认 Advisor 使用的是不带 `lastN` 的 `get(id)`。两种读取都返回独立列表。

默认上限可在 `application.yml` 配置，也可通过 `CHAT_MEMORY_MAX_STORED_MESSAGES` 和 `CHAT_MEMORY_MAX_CONTEXT_MESSAGES` 环境变量调整，重启后生效。自定义存储目录可设置 `APP_CHAT_MEMORY_DIRECTORY`。两个条数都必须为正数，且上下文条数不能超过磁盘条数，非法设置会使应用启动失败。

限制按消息条数计算，不是按字符或 token 计算；单条长消息仍可能占用较大空间。不同会话各有一个文件，本次没有增加闲置会话自动删除或全目录磁盘配额。

## 并发与写入失败

追加消息时，读取旧记录、合并新消息、裁剪并保存都在同一个临界区中执行。读取和清空也使用相同保护，避免保存一半时被读取或清空。

JVM 内只使用一个共享锁，不为每个会话永久创建锁对象。每个存储目录还有一个 `.chat-memory.lock` 文件，通过文件锁协调使用同一目录的多个本地 Java 进程。不要在服务运行时手动删除这个锁文件，否则不同进程可能不再锁住同一个文件。

磁盘操作会短暂排队，模型调用不持有存储锁。多个请求同时使用同一会话时，消息按实际保存顺序追加；存储锁不保证把“一个问题及其完整模型回答”作为整轮排队。该方案适合当前单机文件存储，不承诺不同机器共享网络盘时的锁和原子替换行为。

每次序列化或反序列化使用独立 Kryo 对象。保存先写同目录临时文件并刷入磁盘，再原子替换目标。原子替换不受支持或替换前写入失败时返回错误，保留已有目标文件；不降级为直接覆盖。普通失败会清理临时文件，进程被强制结束时可能留下无效的 `.chat-*.tmp` 文件，这些文件不会被读取为会话。

读取损坏文件时返回错误，不将其当成空历史继续覆盖。错误信息不包含底层异常、消息正文或内部堆栈。仍可显式清空损坏会话后重新开始。

## 旧文件和会话 ID

保留原来的 `.kryo` 文件名及序列化设置。旧版文件在读取时只返回所需窗口，不改写原文件；该会话下次保存时才按新的磁盘上限裁剪。大旧文件在首次读取时仍需完整反序列化。

会话 ID 只允许 1 至 128 个英文字母、数字、下划线和连字符，并排除 Windows 设备名，防止 ID 被解释成目录或特殊文件。前端生成的 UUID 符合此规则。此前使用其他格式 ID 的自定义客户端需要调整 ID。

## 离线验证

- `FileBasedChatMemoryTest`：文件重载、旧格式、消息上限、多线程追加、清空与保存互斥、替换失败、损坏文件及非法 ID。
- `FileBasedChatMemoryProcessTest`：启动两个本地子 JVM，同时向同一临时会话追加 40 条不同消息，检查全部保留。
- `ChatMemoryConfigTest`：默认值、自定义值和启动时配置校验。
- `OpenAiCompatibilityTest`：完整应用配合本地假模型网关，验证同步和 SSE 请求都只发送最近 20 条历史，且不增加模型调用次数。该测试的会话文件全部隔离在临时目录中。
